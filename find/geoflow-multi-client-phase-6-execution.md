### 6D（平台审批与运营流程修订，2026-08-24 产品反馈）

本工作包记录真实试点暴露出的产品流程问题。它不改变客户不登录 GEOFlow、项目授权、发布 gate 或批次状态机的安全边界；目标是让“项目运营上下文”和“平台审批中心”分离，并减少运营人员的重复操作。

#### 6D-1：超级管理员不进入运营项目上下文

- 当前问题：项目上下文接口对超级管理员返回所有 active 项目，顶部切换器因此会加载其他运营人员创建的项目。
- 目标行为：普通管理员只看到自己有 active membership 的项目；超级管理员顶部不加载其他运营人员项目，显示平台全局/无项目上下文。超级管理员如需处理项目资料，必须在具体操作中明确选择目标项目，不能依赖旧 session 或顶部项目切换器。
- 安全要求：隐藏界面不能代替后端授权；项目资源写入仍需明确目标项目，平台级只读/审批页面不得被当前项目上下文错误过滤。

#### 6D-2：超级管理员使用全局发布批次审批中心

- 当前问题：发布批次列表和详情依赖当前项目上下文，超级管理员必须先切换到某个运营项目才能查看该项目批次。
- 目标行为：超级管理员（以及明确配置的 `platform_approver`）进入发布批次审批中心后，默认查看所有运营人员提交的批次，不按当前项目过滤；列表需显示客户、项目、提交人、状态和时间，详情依据批次自身的 `client_project_id` 读取。
- 权限要求：普通管理员仍只能查看自己项目的批次，并且只能创建/提交，不能批准、退回、拒绝或执行平台发布；审批动作必须继续由服务层按批次项目和角色校验，不能通过切换项目绕过。
- 兼容要求：项目内普通运营页面仍可保留项目范围的批次列表；平台审批中心是超级管理员的独立全局视图，不建立第二套批次状态机。

#### 6D-3：任务生成与批次提交自动衔接

- 当前问题：普通管理员创建任务后默认带有按间隔调度，容易被理解为自动公开发布；文章审核通过后还要手动进入批次页面创建批次并提交审核，流程重复且容易遗漏。
- 目标行为：任务的“发布间隔”只控制文章草稿生成/释放节奏，不代表自动公开发布；新项目继续遵守 `platform_approval` gate。文章审核通过后，系统按项目幂等地创建或复用待提交批次，将文章加入批次并自动提交到平台审批中心，普通管理员无需手动创建批次或点击“提交审核”。
- 安全要求：超级管理员批准仍是公开发布前的独立审批；批次快照、文章版本 hash、目标 gate、失败/不确定结果和审计日志继续由现有 batch/item owner 记录。远程渠道写操作和生产发布仍不因自动提交而被触发。
- 待定决策：批准后的“本地执行”是否自动触发、批次按单篇文章还是按时间窗口归集，需在实现前根据运营频率确认；在决策前沿用现有手动、可审计执行方式。

#### 6D 最小验收

- 超级管理员登录后顶部不出现其他运营人员的项目；普通管理员项目切换行为不变。
- 超级管理员无需项目上下文即可看到所有运营人员提交的批次，并能从批次自身项目读取详情和执行既有审批动作；普通管理员无法看到其他项目批次。
- 新建任务的间隔只产生草稿，不绕过 `platform_approval`；文章审核通过后自动生成/复用并提交批次，重复事件不会生成重复批次或重复 item。
- 自动衔接失败时保留稳定失败状态和告警，不能伪造“已提交”；所有既有 focused 回归、权限矩阵和批次幂等测试继续通过。

## 1. 阶段目标

在项目隔离、发布门闸和发布批次合同稳定后，让内部普通运营人员能够在 GEOFlow 内自助建立客户档案和项目，并继续使用现有后台维护知识库、关键词库、标题库和图片库，完成“资料 → 任务 → 文章 → 发布批次”的项目内流程。首个小规模试点完成后，再按项目补充 AI 用量、存储、文章数、并发、队列公平性、告警和聚合报表。

本阶段的 `Client` 是内部客户档案和归属标签，不是客户用户；客户不登录 GEOFlow，不持有 session、Sanctum token 或 API 权限。客户资料如何交付给运营人员不属于本计划，运营人员继续沿用现有后台资料流程。本阶段不建设外部资料接收层、客户 webhook、客户上传 API、客户导入身份或客户门户。

## 2. 拆分后的工作包

### 6A-0：普通运营人员自助创建客户与项目

**目标**

- 允许普通 `operator` 在后台创建客户档案和项目，并自动成为该项目唯一的 active `operator` 成员。
- 创建成功后自动建立项目上下文，使创建者可以立即继续维护资料和创建任务。
- 保证客户档案、项目、成员和上下文的创建拥有一个明确的事务 owner。

**边界**

- `Client`、`ClientProject`、`ClientProjectMember` 必须在一个事务内创建；客户和项目不是登录主体，不能由此创建客户账号、客户 token 或客户 session。
- 入口只允许普通运营人员为自己创建新客户/项目；跨项目批量创建、替他人创建成员关系、管理员分配项目和成员转移另立需求。
- slug/名称唯一性、重复提交和失败回滚由服务层与数据库约束共同保证；不得信任请求体 `project_id` 决定归属。
- 不改变阶段 1 已建立的角色枚举、成员状态和项目停用语义。

**最小验证**

- 普通 operator 成功创建客户、项目和唯一 active operator 成员；任一写入失败时三类记录全部回滚。
- 重复点击、重放请求和并发创建不会产生重复客户、项目或成员；slug 冲突返回稳定校验结果。
- 创建者自动进入新项目上下文；其他未授权 operator 无法通过 URL、请求体、旧 session 或 token 读取/修改该项目。

### 6A-1：项目内现有资料后台流程与严格隔离

**目标**

- 在 6A-0 建立的项目上下文中，继续沿用现有后台创建/上传知识库、关键词库、标题库和图片库的流程。
- 让资料库、条目、作者、分类和文章图片等直接 owner 始终继承当前项目，并复用阶段 2 的资源解析与同项目校验。
- 让运营人员感知为“选择项目后按现在的方式添加资料”，不新增客户操作界面或资料接收层。

**边界**

- 不改变现有资料录入方式；未来批量导入、客户直传和资料外部接收另立需求，不在本阶段顺手引入。
- 未完成项目过滤的页面、导出、详情、上传、更新、删除和批量入口不得向普通 operator 开放；菜单隐藏不能代替后端授权。
- 平台级 AI 模型、敏感词基线和全局站点设置仍由平台 owner 管理，不复制为客户配置。
- 资料失败、重复和部分结果必须记录真实状态，不用全局默认资源掩盖跨项目关系错误。

**最小验证**

- 运营人员在同一项目下通过现有后台完成四类资料的创建、上传、详情、更新和删除；切换项目后不能读写另一项目资料。
- 资料列表、分页、导入、批量操作和必要 API 均按数据库 owner/项目授权过滤；跨项目引用在 Service/事务层被拒绝。
- owner、操作者、重复提交和失败结果可审计；日志、队列 payload 和错误页不泄露客户正文、token 或密钥。

### 6A-2：资料 → 任务 → 文章 → 发布批次全流程回归

**目标**

- 在阶段 3/4 的发布门闸和批次合同已完成后，验证普通 operator 从自建项目开始完成资料准备、任务创建、文章生成/审核和批次提交。
- 证明超级管理员可以在明确项目范围内查看并处理 operator 提交的批次，而 operator 不能批准或执行平台发布。
- 形成真实内部资料试点前的单链路验收证据。

**边界**

- 只复用阶段 2、3、4 已冻结的任务、文章、gate 和 batch/item 状态机，不新增旁路发布入口或修改平台审批规则。
- 只做同项目、内部测试和受控本站回归；不执行未经批准的远程渠道写操作，不向客户展示状态或回执。
- 文章版本变化、目标快照失效、重复提交、失败和不确定结果沿用阶段 4 owner；本包不创建第二套 workflow。

**最小验证**

- 新建项目资料只能被该项目任务引用，生成文章继承同一项目，operator 可以提交批次但不能批准/执行平台发布。
- 超级管理员可处理其他 operator 的批次；文章 hash、目标快照、重复提交、失败/不确定和 item 级结果均可读回。
- 至少完成一条“创建项目 → 添加资料 → 创建任务 → 生成文章 → 审核 → 提交批次”的验收链路，并通过跨项目拒绝后，才允许接入真实内部资料试点。

### 6B：项目级用量、配额、存储与并发限制

**目标**

- 基于阶段 1/2 已建立的不可变 `ai_usage_events`/observation，实施项目级 AI 用量、存储、文章数和并发限制。
- 将 reservation、消耗、释放、失败和不确定调用与项目 quota 关联，保证配额判断不会成为第二个业务事实 owner。
- 为 operator 和 super_admin 提供可审计的项目使用量与拒绝原因。

**边界**

- 事件继续记录 project、model、operation、attempt、units、outcome、fallback 和 reservation 生命周期；平台级 AI Key、模型和敏感词基线仍由超级管理员管理。
- quota 配置和计数必须在明确项目上下文中读取；不得把 project ID、quota、secret 或可篡改余额放进 Job payload、token 或日志。
- 配额拒绝必须是稳定的业务结果，不通过删除任务、伪造成功或修改平台全局 quota 来“释放”容量。
- 首个小规模试点不被 6B 阻塞；没有明确产品额度时只实现 observation、可配置限制和安全拒绝，不擅自制定计费价格。

**最小验证**

- AI 成功、失败、fallback、重试和不确定调用均产生可追溯 usage observation；共享模型消耗可按项目审计且不会重复计费。
- 项目级 AI、存储、文章数和并发达到限制时返回稳定拒绝；重复请求、超时、释放和进程重启不会丢失或重复 reservation。
- 两个项目并发运行时互不消耗对方额度；quota 读写、管理员操作和拒绝原因均有权限与审计测试。

### 6C：队列公平性、失败告警与项目聚合报表

**目标**

- 在共享 Laravel Queue/Redis/Horizon worker 上建立按项目可观察的公平性、优先级和并发控制，避免单个项目长期占满 worker。
- 将任务失败、重试耗尽、stale recovery、配额拒绝和不确定结果形成按项目聚合的告警。
- 提供项目级任务、文章、AI 用量、存储、发布批次和失败结果报表，同时保留平台级总览语义。

**边界**

- 只改造项目级队列调度、标签、限流、告警和查询聚合；不把 Horizon 全局指标改造成客户可见看板，也不复制第二套队列状态机。
- 公平性不能靠修改 Job payload 中的项目 ID；Job 执行时仍从稳定业务 ID 解析项目 owner，队列状态事实仍由现有 Job/TaskRun owner 管理。
- 报表查询必须在数据库层按项目条件、owner join、索引和分页聚合；不先加载全表再由 PHP 过滤。
- 不在本包新增客户登录、客户通知入口、外部资料接收、公开前台或新的渠道连接器；告警只面向内部管理员/运营人员。
- 规模化阈值、优先级和通知渠道没有产品决策时，先落地可观察性、告警事件和安全默认值，不擅自扩大为完整计费系统。

**最小验证**

- 两个或更多项目同时产生任务、重试和长耗时作业时，队列 claim、并发上限、等待时间和吞吐可观察，单项目不能无限挤占共享 worker。
- 失败、重试耗尽、stale recovery、quota 拒绝和不确定结果按项目产生告警；告警去重、恢复和重复消费是幂等的。
- 项目任务、文章、AI 用量、存储、批次和失败聚合可按授权读取；500 个项目查询不读取全表后应用层过滤，并有可重复的索引/查询计划证据。

## 3. 工作包依赖与阶段闸门

```text
6A-0 普通运营自助创建客户/项目
    ↓
6A-1 项目内资料创建/上传与严格隔离

阶段 3 + 阶段 4
    ↓
6A-2 资料 → 任务 → 文章 → 发布批次全流程回归

6A-2 通过后接入真实小规模内部资料试点
    ├── 6B 项目级用量、配额、存储与并发限制
    └── 6C 队列公平性、失败告警与项目聚合报表

真实试点反馈
    ↓
6D 平台审批与运营流程修订
```

6A-0 和 6A-1 是真实资料试点的前置；6A-2 必须等待阶段 3/4 的 gate、batch/item 和执行器合同稳定，不能在批次能力尚未完成时用 mock 流程宣称全链路通过。6B/6C 属于试点后的规模化加固，可以并行，但共享阶段 1/2 的 usage observation、TaskRun 和项目 owner 合同。6D 来源于真实试点反馈，完成前不得把当前“项目内批次页面 + 手动提交”描述为最终运营流程。

### 允许进入真实内部资料试点

- 6A-0 的事务、幂等、项目上下文和自动 operator 成员关系通过；
- 6A-1 的知识库、关键词库、标题库、图片库及作者/分类后台流程在项目范围内可用，跨项目拒绝和失败回滚通过；
- 阶段 2 的任务→文章隔离、阶段 3 的 publication gate 和阶段 4 的 batch/item 最小合同已经通过；
- 6A-2 的完整链路回归通过，operator 只能提交批次，平台负责人才能批准/执行；
- 6D 的平台审批中心、超级管理员项目上下文边界和任务到批次自动衔接通过；
- 客户仍没有登录、token、上传或直连 API，资料由内部运营人员沿用现有后台流程维护。

### 允许进入阶段 7 或规模化运营加固

- 5A–5G 的 Enterprise、URL Import、中央站资格和 identity 合同通过；
- 6B 的 quota、reservation、存储/文章数/并发限制和审计通过；
- 6C 的队列公平性、告警、聚合报表、索引/查询计划和恢复幂等通过；
- 未引入客户通知/管理入口、全局 quota 旁路 writer 或第二套队列状态机。

### 必须停留在阶段 6

- operator 创建项目后无法安全切换上下文，或客户档案被误当作登录主体；
- 现有资料后台仍能跨项目读取、上传、修改、删除或绑定资源；
- 6A-2 依赖的阶段 3/4 合同未完成，或 operator 可以批准/执行平台发布；
- quota/reservation 在重试、并发、失败或不确定结果下重复扣减、丢失或跨项目消耗；
- 一个项目可以长期占满共享 worker，或告警/报表查询依赖全表内存过滤；
- 只完成界面流程而没有事务、授权、幂等、队列和报表的最小验证证据。

## 4. 阶段 6 交付物

阶段 6 完成时只允许产生以下结果：

1. 普通 operator 自助创建客户档案/项目和项目上下文的内部能力；
2. 现有知识库、关键词库、标题库和图片库后台流程的项目隔离回归；
3. 资料→任务→文章→发布批次的内部全流程验收证据；
4. 项目级 usage observation、quota、存储、文章数和并发限制；
5. 项目队列公平性、失败告警、聚合报表和查询性能证据；
6. 真实小规模内部资料试点的边界、回滚和后续规模化风险清单。

不得在阶段 6 产生客户登录/上传、客户 token、客户直连 API、外部资料接收层、客户通知入口、完整项目官网或无明确产品决策的批量导入/计费系统。

## 5. 执行方式

本助手按 `6A-0 → 6A-1 → (阶段 3/4) → 6A-2 → (6B/6C) → 6D` 执行。每个工作包开始前先核对阶段 1–5 的实际 owner、迁移、项目上下文、gate/batch 和队列合同；完成后先运行该包最小验证，再更新本文件和总计划。真实内部资料试点只在 6A-2 闸门通过后进行；6D 根据试点反馈收敛平台审批和运营流程；客户资料的外部交付方式不在本计划内。
