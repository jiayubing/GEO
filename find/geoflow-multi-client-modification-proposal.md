# GEOFlow 多客户 GEO 服务改造方案建议

> 调研日期：2026-08-22  
> 适用版本：当前工作区 GEOFlow 2.3.0 代码与已部署管理站  
> 文档性质：后续改造建议，不代表已经完成开发或已经具备多租户能力

> 文档状态：历史业务方案与目标流程参考，不作为当前代码实施依据。现行技术总计划以 [`geoflow-multi-client-implementation-audit.md`](./geoflow-multi-client-implementation-audit.md) 为准；各阶段的具体执行顺序、边界、验收标准和当前状态以对应的 `geoflow-multi-client-phase-*-execution.md` 文档为准。

## 0. 与现行实施计划的关系

本文先于实现审计与分阶段执行计划形成，保留的是业务目标、角色分工和最终产品方向。后续源码审计对资源 owner、项目上下文、发布门闸、发布批次和阶段顺序进行了细化与修订，因此本文中的阶段编号和能力归属不能直接用来安排开发工作。

当前文档使用规则：

- 用本文理解“运营人员生产、平台负责人审批发布”的业务愿景，以及客户、项目、员工三者的关系。
- 用 [`geoflow-multi-client-implementation-audit.md`](./geoflow-multi-client-implementation-audit.md) 判断当前应该做什么、何时进入下一阶段，以及哪些能力明确尚未实现。
- 用对应阶段执行文档实施和验收；如果本文的业务目标与现行技术计划发生冲突，应在下一阶段开始前先修订技术计划，不应直接按本文增加旁路功能。
- 本文所称“平台负责人/超级管理员”是业务职责描述；代码中的具体角色映射、项目授权和审批权限以现行技术计划及阶段 4 的发布批次合同为准。

## 1. 结论先行

你的业务方向是合理的：运营人员负责客户资料、生成和内容审核，平台负责人统一控制本站发布和外部渠道分发。这比“让 500 个客户各自登录后台”更适合 GEO 服务商。

但需要修正两个关键假设：

1. 客户不能用“一个管理员账号”来代表隔离边界。账号代表人，客户应由独立的“客户项目”代表；一个运营人员可以负责多个项目，一个项目也可以由多个运营人员协作。
2. 平台负责人不应只看到一个数字就盲目发布。可以把日常审核交给运营人员，但发布队列至少要显示客户、文章数量、目标渠道、风险/失败例外和最近审核人，并支持按项目批量发布。

因此建议的目标不是“每个客户一套 Docker”，也不是“多个 admin 账号”，而是：

> 一套 GEOFlow + 客户/项目工作空间 + 运营人员项目权限 + 自动入库/生成 + 运营审核 + 平台发布队列 + 按项目分发配置。

这需要真正的多项目/多租户改造。当前版本不能通过配置开关直接实现。

## 2. 当前代码能否直接支持你的流程

| 业务要求 | 当前情况 | 判断 |
| --- | --- | --- |
| 运营人员分别维护不同客户资料 | 知识库、关键词库、标题库、图片库、任务、文章均为全局表；后台普通管理员登录后访问同一批数据 | 不能安全直接使用 |
| 每个客户单独账号隔离 | `admins` 只有角色和登录信息，没有客户/项目归属；普通账号不是工作空间 | 不可行 |
| 运营人员生成后审核 | 文章有 `review_status`，任务有 `need_review`，可支持人工审核 | 可复用 |
| 提交给平台负责人统一发布 | 现有文章可审核/发布，分发队列也存在，但没有“按客户提交批次”的对象和统计 | 需要增加提交队列 |
| 平台负责人看到每个客户待发布数量 | 当前文章列表只能按任务、状态等筛选，没有客户项目维度 | 需要增加项目维度和聚合看板 |
| 自动分发到渠道 | 已有 GEOFlow Agent、WordPress REST、Generic HTTP API 和队列 | 可复用，但必须增加项目到渠道的映射 |
| 客户没有官网也能服务 | 文章可以只分发渠道，也可以发布到 GEOFlow 本站 | 可实现，但本站发布必须按项目显式开启，不能默认把所有客户内容放到服务商官网 |
| 500 个客户仍能维护 | 当前没有客户级存储、文章、AI 调用、并发或生成配额，也没有批量入库/模板化开户 | 需要自动化改造 |

关键源码证据：

- 业务表定义位于 `database/migrations/2026_04_18_120000_geoflow_legacy_schema.php`。`keyword_libraries`、`title_libraries`、`knowledge_bases`、`tasks`、`articles` 等没有统一的客户/项目字段。
- `app/Models/Admin.php` 的角色判断只有 `admin`/`super_admin` 语义，没有项目成员关系。
- `routes/web.php` 中任务、文章、素材、知识库等主要路由只经过 `admin.auth`；普通管理员并不会自动获得客户范围过滤。分发管理虽然是超级管理员路由，但这只是操作权限，不是客户隔离。
- `routes/api.php` 的 scope（例如 `materials:read`、`tasks:write`、`articles:publish`）控制“能不能读写某类资源”，不控制“只能读哪个客户”。
- `app/Services/GeoFlow/MaterialLibraryService.php`、`TaskLifecycleService.php`、`ArticleGeoFlowService.php` 的查询按资源 ID/状态执行，没有项目上下文。
- 现有 `manual_publications.assigned_admin_id` 只能分配人工外部发布工单；不能把知识库、标题库、任务和文章隔离成客户空间。
- `enterprise_knowledge_projects.created_by_admin_id` 记录创建人，但不是客户边界，也没有对其他业务表的统一过滤。

本机主机没有 PHP CLI，无法在当前 Windows shell 重新运行 `artisan route:list`；本次判断以当前工作区源码、迁移、路由和前序已登录管理站证据为准，未进行写入或生产操作。

## 3. 建议采用的业务模型

### 3.1 客户、项目、员工是三个不同概念

不要把“客户”和“账号”混成一个表：

```text
客户 Client（商业关系）
  └── 项目 Project（一个品牌/业务线/网站或内容计划）
        ├── 知识库、关键词库、标题库、图片库
        ├── 任务与生成文章
        ├── 运营人员成员
        └── 发布配置与渠道映射

员工 Admin（公司人员）
  └── 通过 project_members 负责一个或多个项目
```

这样可以处理“同一客户有多个品牌”“一个运营人员负责多个客户”“人员离职后转交项目”等真实情况。客户暂时不需要登录；如果将来开放自助，再单独增加客户门户身份，不把客户直接放进现有 `admins` 管理后台。

### 3.2 哪些资源应按项目隔离

第一阶段至少给下列资源增加 `client_project_id`（名称可按代码规范确定），并在创建、读取、更新、删除、列表、导入、队列和分发时强制带项目上下文：

- `knowledge_bases`、`knowledge_chunks`
- `keyword_libraries`、`keywords`
- `title_libraries`、`titles`
- `image_libraries`、`images`
- `tasks`、`task_knowledge_bases`、`task_runs`
- `articles`、`article_images`、`article_reviews`
- 企业知识项目及 URL 导入任务

`categories`、`authors` 是否按项目复制，要根据运营方式决定；如果不同客户的分类/作者品牌不同，应项目化。如果只是公司统一的作者和分类，可保留全局，但文章仍必须保存项目归属。

下列通常应保持平台级，不应让普通运营人员自行修改：AI Provider 密钥、模型连接、全局提示词基线、敏感词基线、分发渠道密钥、系统设置和管理员账号。若未来允许客户定制提示词，应增加“平台模板 + 项目覆盖”的明确优先级，而不是让每个项目直接修改全局提示词。

### 3.3 不能只给文章增加项目字段

如果只在 `articles` 加客户字段，任务仍可能把客户 A 的标题库或知识库用于客户 B，队列也可能生成错误文章。因此必须验证整条引用链：

```text
项目
  → 素材库
  → 任务
  → 任务可引用的知识库集合
  → 文章
  → 发布提交
  → 目标站点/渠道
```

例如，任务绑定知识库时必须检查两个资源属于同一项目；文章从任务生成时从任务继承项目，不允许由请求体随意覆盖。

## 4. 推荐的运营工作流

### 阶段 A：客户资料进入项目

运营人员先选择客户项目，而不是直接在全局“知识库”页面凭名称猜库。资料入口应支持：

- 单个文件/Markdown/文本上传；
- 批量 ZIP 或 manifest 导入；
- 后续再增加 Webhook/API，由客户提交资料而不是登录 GEOFlow；
- 文件指纹、来源、版本、上传人和导入结果记录，避免重复导入。

客户编号只用于搜索和显示，不能作为安全边界；真正的边界必须是数据库字段、授权策略和查询过滤。

### 阶段 B：一键创建或复用生成配置

不要让运营人员为每个客户重复手工点几十个页面。建议提供“项目开户/内容包”向导：

1. 创建客户项目；
2. 创建或导入知识库、标题库、关键词库、图片库；
3. 选择平台批准的模型和提示词模板；
4. 生成任务模板（文章数量、审核开关、发布频率、分类策略）；
5. 试生成 1 篇；
6. 通过后再批量入队。

API v1 可以复用来做部分材料、任务和文章操作，但必须先增加项目授权；不能把现有全局 API Token 直接发给客户或用它代替租户控制。

### 阶段 C：运营审核

生成文章先保持当前文章 `review_status` 机制，运营人员检查事实、品牌口径、SEO 字段、敏感/风险内容和重复度。审核通过后，运营人员执行“提交发布批次”，而不是一篇篇给平台负责人发消息。

建议一个提交批次包含：项目、文章集合、请求的本站/渠道目标、提交人、提交时间、备注和版本快照。提交后，运营人员不能悄悄修改已经提交的正文；如需修改，应生成新版本或撤回批次。

### 阶段 D：平台负责人发布队列

平台负责人首页应看到：

- 每个客户/项目待发布文章数；
- 目标是本站、哪些渠道；
- 已通过运营审核的文章数、风险阻断数、失败重试数；
- 最近提交人和时间；
- 可按项目批量批准、发布、退回；
- 需要人工关注的异常文章列表。

这里可以让平台负责人日常只处理数量和例外，不必逐篇重做运营审核，但不能完全看不到文章摘要、目标渠道和风险状态。对于高风险客户或新项目，可配置“全量复核”；成熟项目可配置“抽样复核/异常复核”。

### 阶段 E：本站与渠道分发

当前已有任务发布范围和分发队列，可以继续使用，但增加项目级发布配置：

- 项目是否允许发布到服务商中央站；
- 项目对应哪些 GEOFlow Agent/WordPress/Generic HTTP API 渠道；
- 哪些文章类别可以分发到哪个渠道；
- 平台负责人是否允许覆盖目标；
- 分发成功、远端成功、结果不确定分别记录。

没有官网的客户，默认不应自动发布到你的中央官网。可选策略是“仅渠道分发”或“项目明确开启中央站的独立栏目/路径”。否则客户内容会混在服务商官网上，带来品牌归属、SEO、版权和下线责任问题。

外部渠道密钥必须继续由超级管理员维护；运营人员只能看到渠道名称和健康状态，不能读取密钥。

## 5. 需要新增的核心能力

### 5.1 权限与隔离

建议增加：

- `clients`、`client_projects`；
- `project_members(admin_id, project_id, role)`；
- 项目级 Policy/授权服务；
- 所有项目资源的统一查询入口或显式 `whereProject(...)`；
- 项目级 API Token（Token 既有 scope 又绑定项目）；
- 文件目录、缓存键、幂等键、任务 payload 和日志中的项目上下文。

超级管理员可跨项目查看和发布；运营人员只能访问被分配项目；普通运营人员不能管理 AI 密钥、渠道密钥、管理员和系统更新。

### 5.2 发布提交与批次

建议新增 `publication_batches` 与 `publication_batch_items`，或等价的发布提交模型。不要把“运营审核通过”和“平台批准发布”复用成同一个字段：

```text
文章内容审核：pending → approved / rejected
发布提交批次：draft → submitted → approved / returned → publishing → completed / partial / uncertain / failed
```

批次需要保存项目、提交人、审核人、目标快照、文章版本、幂等键和状态变更日志。这样平台负责人可以按项目统计数量，也能在远程分发结果不确定时暂停重试，符合当前系统对远程副作用的安全要求。

### 5.3 批量接入、模板和配额

500 个客户的瓶颈不是创建 500 个账号，而是资料接入和配置重复。应增加：

- 项目开户模板/内容包；
- 批量文件导入和错误报告；
- 资料版本与归档；
- 每项目资料大小、文章数、AI 调用量、并发任务数和存储配额；
- 全局队列并发上限、项目优先级和失败告警；
- 项目级统计：待生成、生成失败、待运营审核、待平台发布、已发布、分发失败。

当前 GEOFlow 的单文件上传约 2 MB、单任务知识库选择最多 5 个等限制是单次操作保护，不是客户容量管理，不能把它们误认为已经有客户配额体系。

## 6. 对你提出的方案逐条判断

### “运营人员只负责上传、生成、提交发布”

方向合理，但应再加两项职责：资料版本/来源确认，以及提交前的项目级校验。否则运营人员可能把资料上传到错误项目，或者提交一个没有目标渠道、没有有效作者/分类、已有失败分发任务的批次。

### “超级管理员只看每个客户需要发布多少篇”

作为日常工作台是合理的；作为唯一发布依据不安全。至少保留文章摘要、目标渠道、风险状态、版本、运营审核人和异常原因。推荐“正常项目按批次发布，异常项目逐篇复核”的策略。

### “通过多个账号隔离客户”

不合理。当前普通账号只解决登录和操作审计，不解决数据隔离；员工离职、多人协作、客户转交和 API 自动化都会让这种方案失效。账号应绑定员工，项目应绑定客户。

### “没有官网的客户也统一发本站”

不应默认这样做。中央站发布是你的公开品牌资产，不等于客户官网。应由项目发布配置明确选择：中央站、指定客户站点、仅外部分发，或暂不公开。

### “后期再考虑多客户能力”

可以先做小范围试点，但试点也不应把真实客户资料放进没有项目边界的生产库。至少先建立客户项目清单、项目编号、运营分工和资料导入 SOP；若进入付费客户阶段，应先完成项目隔离和发布队列的最小版本。

## 7. 分阶段改造建议

### 第 0 阶段：小规模验证

- 只让公司员工使用，不开放客户直接登录；
- 选择 3–5 个低风险客户做试点；
- 每个客户先建立一个项目，统一使用项目编号；
- 暂不开启中央站自动公开，先用 `local_only`/草稿或测试渠道验证内容质量；
- 记录每个项目的资料量、生成耗时、人工审核耗时、失败率和分发成功率。

如果这一阶段仍需要运营人员靠搜索名称避免选错客户，说明产品边界尚未达到生产要求。

### 第 1 阶段：最小可用项目隔离

优先实现：

1. 客户/项目表和项目成员关系；
2. 知识库、标题库、关键词库、任务、文章的项目归属；
3. 运营人员项目权限和跨项目访问测试；
4. 任务、队列、文件、API 的项目上下文；
5. 运营审核后的发布提交批次；
6. 平台负责人按项目聚合查看和批量发布；
7. 项目到本站/渠道的发布配置。

这一阶段完成前，不应把“普通 admin 账号”当作客户隔离方案。

### 第 2 阶段：规模化运营

- 内容包/模板开户；
- 批量导入、Webhook/API、幂等与重复资料检测；
- 项目配额、生成优先级、队列监控、失败告警；
- 文章版本、批次撤回、分发结果对账；
- 项目级报表和运营绩效。

### 第 3 阶段：可选客户门户与官网

只有在客户确实需要自助提交或查看进度时，才增加受限客户门户。客户门户只允许访问自己的项目资料和文章状态，不暴露平台 AI Key、全局素材、分发密钥和其他客户数据。需要独立官网的客户，再按项目绑定 WordPress、GEOFlow Agent 或其他渠道。

## 8. 必须具备的验收测试

改造不能只通过页面演示验收，至少需要以下行为测试：

1. 运营人员访问未分配项目的知识库、任务、文章、文件和 API，均得到拒绝或不存在，不是只在前端隐藏下拉框。
2. 任务不能绑定另一个项目的知识库、标题库、关键词库、图片库或渠道。
3. 生成队列重试、重启和并发时，项目上下文不会丢失；文章始终继承任务项目。
4. 运营审核通过后提交批次；批次中的文章被修改时必须产生新版本或要求重新提交。
5. 平台负责人可按项目查看待发布数量、批量批准和批量分发；重复点击不会重复发布。
6. 本站发布、远程渠道成功、远程结果不确定、远程失败分别显示，不把不确定结果盲目当失败重试。
7. 禁用或移交运营人员后，项目数据仍保留，新的成员可接管，历史操作审计不丢失。
8. 旧数据迁移到“legacy project”后，原有单客户部署的文章和任务仍能生成、审核、发布。

## 9. 最终建议

可以采用你提出的“运营审核、平台统一发布”的业务分工，但不要直接在现有后台上通过多个账号和命名规则拼出隔离。正确的最小产品是“项目化运营 + 发布批次 + 平台级分发”，客户账号和独立官网都可以后置。

对当前项目的下一步，建议先做设计评审和数据边界清单，再决定是否在现有仓库实现第 1 阶段；不要先改页面下拉框，也不要先批量导入 500 个客户资料。只要项目归属、查询过滤、队列上下文和发布提交没有同时落地，规模化使用就存在跨客户泄露和误发布风险。
