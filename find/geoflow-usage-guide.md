# GEOFlow 2.3.0 本地项目能力与使用指南

> 调研日期：2026-08-22  
> 本地管理站：<http://localhost:18080/geo_admin/dashboard>  
> 依据：当前工作区源码、README、Laravel 路由定义，以及登录后的管理站页面（账号密码仅用于本地登录，本文不记录密码）。

## 1. 一句话理解

GEOFlow 是一个“可信资料 → AI 内容生产 → 人工审核 → 本站发布 → 多站分发 → 访问/AI 爬虫归因”的 GEO（生成式引擎优化）内容工程系统。它不是单纯的文章生成器，核心价值在于把知识资产、提示词、模型、队列、审核、SEO 页面和外部分发组织成可追踪的生产链。

运行链路：

```text
AI/提示词配置 + 知识/标题/关键词/图片/作者资产
        ↓
任务与队列（Worker/Redis）
        ↓
草稿 → 人工审核 → 本站发布
        ↓
GEOFlow Agent / WordPress REST / 通用 HTTP API 分发
        ↓
访问日志、AI 爬虫识别、品牌可见率、线索转化分析
```

## 2. 能实现什么

### 内容与知识资产

- 知识库：新建、上传 Markdown/Word 文档、编辑 Markdown、刷新语义切片；可配置 embedding 后进行向量化和 RAG 召回。
- 企业知识原子化：把官网、产品手册、FAQ、案例等资料整理为“主张、证据、上下文、风险、待确认项”，人工校对后发布为正式知识库。
- 标题库、关键词库、图片库、作者库：支持手工录入、导入或 AI 生成标题；为任务提供可复用输入。
- 正文提示词与特殊提示词：分别控制正文、关键词、描述等生成策略。
- URL 智能采集：输入公开文章/报告 URL，解析后可生成知识库、关键词库和标题库；当前页面明确要求先配置可用 AI 模型。

### AI 与自动化生产

- 支持 OpenAI-compatible 与 Gemini 原生接口；chat/embedding 模型、连接测试、默认 embedding、切片策略和模型统计。
- 任务可设置标题库、提示词、模型、知识库、作者、图片数量、生成数量、草稿上限、审核开关、发布间隔、循环执行等。
- 支持固定模型或智能故障切换，后台队列负责生成、失败重试和状态记录；队列驱动为 Redis。

### 审核、发布和人工发布

- 文章管理覆盖草稿、待人工审核、人工通过/拒绝、已发布、私有、垃圾箱、恢复和批量操作。
- 文章包含 SEO 字段、关键词、作者、分类、任务来源；本站前台输出文章详情、Open Graph、Schema、Markdown、sitemap/TXT 地图等 SEO/LLM 友好内容。
- “人工发布”工作台可把文章或评论文案编成外部平台手工执行工单，记录身份、执行人、计划时间、风险提示、发布回执和 CSV；系统不保存外部平台密码、Cookie 或 OAuth 凭证。

### 多站点分发

- 渠道类型：GEOFlow Agent、WordPress REST、Generic HTTP API。
- 支持连接健康检查、密钥/应用密码安全存储、暂停/启用、分发队列、重试、日志、远端文章更新/删除。
- GEOFlow Agent 可生成目标站点 PHP 包，包含首页、详情页、静态资源、sitemap、`llms.txt`/TXT 地图、Schema，并支持静态或伪静态模式及站点设置同步。
- 任务发布范围可选：本站+渠道、仅渠道、仅本站；仅本站不会进入远程队列。

### 分析与站点运营

- 增长中心专题：总览、内容运营、流量归因、AI 可见性、线索转化、多站分发。
- 可观察真实访问、独立 IP、AI/API 调用、AI 爬虫、Top 内容、任务健康、分发成功/失败和趋势。
- 线索表单与线索管理：创建/启用表单、前台提交、跟进状态、详情与导出。
- 网站设置：站点标题/SEO/版权、安全敏感词、主题激活、首页模块、文章详情广告；主题复制/预览/发布流程受权限和预览约束。
- 系统更新中心：检查 GitHub 版本、生成计划、备份和回滚诊断；Docker 镜像部署应按重新构建镜像升级。

## 4. 推荐首次使用顺序

### 第一步：先校正部署与安全

1. 在 Docker Compose 的环境文件中确认 `APP_URL`、`APP_PORT`、`ADMIN_BASE_PATH`、数据库、Redis、队列配置。
2. 首次登录后立即修改默认管理员密码；不要把管理员密码、Provider API Key、渠道密钥写进文档或日志。
3. 确认队列/Worker/调度器容器正在运行；否则“创建任务”只会产生待处理状态而不会生成文章。

### 第二步：配置 AI

进入 `/geo_admin/ai-models`：

1. 添加至少一个可用 chat 模型，填写 Provider、API 地址、模型名和密钥。
2. 点击连接测试，确认模型状态为可用。
3. 如要知识库 RAG，再添加 embedding 模型并设置默认 embedding；选择结构化切片或自动/语义规划策略。
4. 在 `/geo_admin/ai-prompts` 和 `/geo_admin/ai-special-prompts` 检查正文、关键词、描述提示词。

### 第三步：建设真实知识资产

优先在 `/geo_admin/knowledge-bases` 导入真实、可核验、允许使用的资料，再刷新切片；补充标题库、关键词库、作者和图片。资料质量决定生成内容质量，系统不会替代事实核验。

可选：在 `/geo_admin/enterprise-knowledge` 做企业资料原子化，或在 `/geo_admin/url-import` 采集公开文章/报告（需要 AI 模型）。URL 采集完成后应先预览、核验，再提交入库。

### 第四步：创建小规模任务

进入 `/geo_admin/tasks/create`，先设置少量文章、草稿或人工审核模式，选择知识库/标题库/关键词库、模型、作者和分类。首次建议：

- 生成数量设置为 1–3；
- 打开人工审核，不直接自动发布；
- 发布范围先选“仅本站”；
- 先观察生成质量、引用依据、SEO 字段和队列日志。

### 第五步：审核与本站发布

在 `/geo_admin/articles` 检查标题、正文、事实、引用、风险表达、关键词、描述、作者和分类。确认后再通过审核并发布；使用文章详情链接验证本站实际页面，而不是只看后台状态。

### 第六步：配置分发（可选）

进入 `/geo_admin/distribution/create`，按目标类型配置 GEOFlow Agent、WordPress REST 或 Generic HTTP API。先做连接/健康检查，再只绑定一个测试渠道，观察 `/geo_admin/distribution/jobs` 的队列、远端响应和文章 URL。GEOFlow 本地成功与远端成功要分开判断；不要在未确认远端结果时盲目重试。

### 第七步：建立增长闭环

创建并启用 `/geo_admin/lead-forms` 表单，将表单模块放入首页；再到 `/geo_admin/analytics` 查看内容、流量、AI 可见性、线索和多站分发数据。当前实例没有访问/AI 爬虫/线索数据属于正常的空状态，不应把 0 解读为功能失效。

## 6. API/自动化边界

源码中的 `/api/v1` 主要覆盖登录、catalog、任务/Job、材料和文章 CRUD，以及任务启动/停止/入队、文章审核/发布/回收。分发渠道、企业知识、增长中心、线索、URL 采集、主题编辑/复制、系统更新、用户/Token 管理等主要是登录后的 Admin Web 能力，不应自行猜测 API 路径或绕过 CSRF/权限。

## 7. 重要风险与限制

- GEOFlow 的效果取决于真实知识库、内容审核和持续维护；批量生成不等于高质量 GEO。
- AI Provider 密钥、WordPress Application Password、Agent 密钥、API Token 属于敏感信息，应只在后台配置并避免导出。
- 发布、分发、删除、主题发布、系统更新/回滚属于有副作用操作；先预览/测试、确认目标，再执行并回读结果。
- 远端请求已发出但结果不确定时，必须先查分发日志/远端对象状态，不能把“不确定”当成失败自动重试。
- 生产升级使用 Docker Compose 重建镜像并备份数据；当前更新中心明确把本实例识别为不可变 Docker 镜像。
- 仓库 README 提供的是项目能力范围；本地页面才是当前实例可用状态的优先证据，二者不一致时以本地路由和页面为准。

## 9. J4125 服务器是否够用

如果是常见的 Intel Celeron J4125（4 核 4 线程、低功耗）并且平时不超过 5 人使用，**运行 GEOFlow 的后台、公开前台、PostgreSQL、Redis、队列和定时器基本够用**。AI 生成通常调用外部 Provider，主要等待网络和模型返回，因此不会把 J4125 当作本地大模型推理服务器使用。

建议：

- 内存至少 8 GB；4 GB 只能做轻量演示，Docker + PostgreSQL/pgvector + 多个 Worker 容易产生内存压力。
- 使用 SSD，数据库、Docker volume、日志和上传文件不要放机械硬盘。
- 只保留必要服务；Reverb、system-update-queue、knowledge-queue 等可按实际需要运行，但不要在 J4125 上部署本地大语言模型。
- 生成任务采用低并发、少量批次（例如一次 1–3 篇），不要让多个知识解析、向量化、主题复刻和文章生成任务同时运行。
- 正式部署使用 `docker-compose.prod.yml` 的 Nginx + php-fpm 方案，并配置备份、监控和队列失败告警。

可能成为瓶颈的场景：同时大量生成文章、批量 URL 采集/知识库向量化、主题复刻、图片处理、多人同时上传大文件，或在同一台机器上运行媒体服务/虚拟机/本地 AI 模型。此时优先增加内存、限制 Worker 并发，必要时把 PostgreSQL/Redis 或 AI 任务迁移到更强的机器。

综合判断：**5 人以内的轻量内容团队、低频自动生成和一个官网，J4125 可以作为生产服务器；它适合“小规模稳定运行”，不适合高并发内容工厂或本地模型推理。**

## 10. 为多个客户提供 GEO 服务：当前版本的隔离结论

当前 2.3.0 **不是多租户 SaaS 模型**。后台管理员账号主要是登录、角色和操作审计；源码中的关键词库、标题库、知识库、提示词、AI 模型、任务、文章、站点设置和分发渠道表没有统一的客户/租户字段，后台列表也不是按登录账号自动过滤。

因此，单纯给每个客户建立一个后台账号，不能保证客户 A 看不到或改不了客户 B 的知识库、关键词、标题和文章。普通 `admin` 角色与 `super_admin` 的区别主要是权限/受保护操作，不等于客户工作空间隔离。API Token 的 scope 也是读写能力范围，不是租户边界。

当前可行且安全的方案是：**每个客户独立一套 GEOFlow 实例（独立 Docker Compose、数据库、Redis、storage、域名和备份）**。这样知识库、素材、任务、文章、站点设置、AI 密钥和渠道天然隔离。J4125 可以承载少量客户实例，但需要根据内存和磁盘评估；如果客户数量增加，建议把实例迁移到更强的主机或拆到不同服务器。

如果必须“一套后台服务多个客户”，这不是配置问题，而是需要开发真正的多租户能力：租户表、所有业务表的 `tenant_id`、统一查询 scope、任务/队列上下文、文件路径、缓存键、AI 模型与密钥、分发渠道、站点设置、文章公开域名和分析数据都必须带租户边界，并补充跨租户访问回归测试。在完成前，不应把单实例多账号当作客户隔离方案。

### 上百客户时的实际建议

不需要为每个客户创建 Docker 容器。更合理的目标是“一套 GEOFlow 应用 + 一个 PostgreSQL 集群 + 一个 Redis + 共享队列”，通过租户上下文隔离客户数据；客户的公开官网用域名/子域名映射到各自的 tenant，后台则按客户工作空间显示。

第一阶段应优先改造：`tenants`、`tenant_admins`、知识/标题/关键词/图片/作者/提示词/模型/任务/文章/分发渠道等表的租户归属；再改查询、创建、更新、删除和队列 Job。第二阶段处理租户域名、站点设置、文件目录、缓存键、API Token、统计分析和客户端权限。任何一个业务入口漏掉租户过滤，都可能造成跨客户数据泄露。

数据库可先采用共享表 + `tenant_id`（成本最低、适合数百客户），并在 PostgreSQL 增加约束/Row-Level Security 作为第二道防线。不要只依赖前端下拉框、URL 参数或“客户自己记住不要选错库”。

J4125 可以继续承载低并发的共享应用，但上百客户的瓶颈会转为数据库、磁盘、队列积压、备份和公网带宽，而不是登录人数。建议把生成任务限制为按租户配额、全局并发上限和优先级队列；后续把 PostgreSQL/Redis 或 AI 任务迁移到更强服务器，而不改变租户模型。

### “客户提交，你统一执行”的折中模式

如果客户不需要独立官网，可以先采用中央运营模式：客户只提交知识库资料、关键词、标题或文章草稿；你/运营团队在 GEOFlow 中统一导入、创建任务、审核、发布和分发。当前版本的文章审核状态与分发队列可以支持后半段流程，但没有现成的“客户提交箱/客户项目空间”安全隔离模块。

最稳妥的短期做法是不给客户 GEOFlow 后台账号，使用独立的客户编号和外部提交入口（表单、工单系统、网盘目录或定制上传页）。运营人员收到后，在后台建立对应资料和任务，使用命名规则标识客户，生成后统一审核；文章通过后再由超级管理员控制本站发布或进入指定分发渠道。

如果希望客户自己登录并上传资料/创建文章，则至少需要开发一个受限客户门户和待审核队列。不能直接把现有 `admin` 账号发给客户：当前管理员账号不是客户空间，普通账号也不会自动隔离知识库、关键词库、标题库、文章或任务。命名规则只能帮助人工识别，不能作为安全边界。

### 500 客户时不能靠人工后台操作

你的判断正确：500 个客户时，由一个人逐个导入知识库、标题、关键词，再逐个创建任务，运营成本不可接受。可行的目标应是“客户自助提交 + 自动创建客户项目 + 你只做审核和发布”。

当前代码中的硬限制主要是单次操作限制，不是客户容量管理：默认单文件上传上限约 2 MB（`GEOFLOW_MAX_UPLOAD_BYTES`），语义切片单 Job 有字符/切片保护，单个任务最多选择 5 个知识库；没有按客户的资料库总量、文章量、调用量和存储配额，也没有客户项目分组/租户字段。

更合适的改造是增加“客户项目”层，而不是让客户直接使用全局 Admin：客户提交资料后自动创建 `client_project`，项目下挂知识库、标题库、关键词库、任务和文章；客户只能访问自己的提交与状态；超级管理员看到全部项目，执行审核、发布和分发。客户不需要独立官网时，所有已批准文章可以统一发布到中央官网，或由你按项目选择分发渠道。

自动化入口可以是客户门户/API/Webhook：客户上传文件、粘贴资料、提交标题/关键词或文章后，系统自动入库、切片、生成标题/任务并进入待审核队列。现有 API v1 能覆盖一部分材料、任务和文章 CRUD，但 Token scope 不是客户隔离，不能直接把现有 API Token 发给客户作为最终方案；需要在 API 层加项目权限和租户过滤。

## 9. 对“官网开放”和“自动分发”的补充核验

- **可以作为官网对外开放。** 当前实例根路径 `/` 已经是公开前台首页，能看到站点名称、导航、精选文章、最新文章和搜索；已发布文章使用 `/article/{slug}` 公开访问，分类、归档和公开表单也有对应前台路由。要让互联网用户访问，需要把 Docker 的端口通过域名/反向代理/防火墙暴露出去，并把 `APP_URL` 改成实际公网地址；`localhost` 只对本机可见。
- **自动生成后可以自动发布到本站。** 任务创建页有“发布频率（分钟）”，说明系统按间隔从草稿池中发布已通过审核的文章；任务还可以循环生成、设置总文章上限和草稿池上限。
- **自动分发不是只能人工发布。** 任务创建页的“发布范围”提供“本地和渠道站点同时发布”“仅发布到渠道站点”“仅发布到本站”。配置 GEOFlow Agent、WordPress REST 或 Generic HTTP API 渠道后，文章发布可进入远程分发队列，系统记录队列状态、日志和失败重试。
- **人工发布是另一条并行流程。** “人工发布”用于需要运营人员在外部平台手工发帖/评论的场景，不是自动分发的前置条件。它会生成工单、执行人和发布回执；不会自动登录第三方平台。
- **审核会影响自动发布。** 若任务勾选“需要人工审核后才能发布”，生成文章先进入审核/草稿状态，只有审核通过后才可按发布频率自动发布；首次上线建议开启该选项。远程分发还需先有可用渠道，当前本地实例暂时没有渠道。
