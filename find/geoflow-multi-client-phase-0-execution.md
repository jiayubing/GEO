# GEOFlow 多客户改造：阶段 0 独立执行计划

> 关联总计划：[geoflow-multi-client-implementation-audit.md](D:/GEOFlow-2.3.0/find/geoflow-multi-client-implementation-audit.md)
>
> 执行模式：GEOFlow `development` / 只读发现与数据预检
>
> 当前状态：计划已拆出，尚未执行任何数据库、迁移、发布或资料导入操作

## 1. 阶段目标

在修改生产代码或数据库前，锁定本次实施的真实代码版本、运行时能力、数据库结构和旧数据归属风险，并完成渠道归属模型决策。阶段 0 的产物必须能直接指导阶段 1 的迁移和 legacy 回填；不能用假设数据或静态猜测代替运行时证据。

阶段 0 只做发现、只读查询和决策记录，不创建客户/项目，不写迁移，不导入资料，不启动队列，不发布文章，不调用外部渠道写接口。

## 2. 拆分后的工作包

### 0A：版本、工作区和运行时合同盘点

**目标**

- 确认当前工作区实际 commit、分支、未提交变更和与计划所依据版本的差异。
- 盘点 Laravel/PHP、数据库驱动、队列、AI SDK、路由、CLI、迁移和测试能力。
- 识别当前环境中可执行与不可执行的发现命令，并将缺失能力列为验证缺口。

**边界**

- 只读读取 `composer.json`、锁文件、配置样例、路由、迁移、模型、服务、Job、CLI 和测试。
- 优先运行 GEOFlow 提供的 workspace discovery；脚本不存在或依赖不可用时，记录缺失，不自行复制脚本或伪造输出。
- 不读取或输出 API Key、Cookie、Token、数据库密码、渠道 secret 或客户资料正文。

**最小验证**

- 生成版本与能力清单：代码版本、数据库类型、队列/AI 能力、可用路由/CLI、未验证项和原因。
- 清楚标注“已通过静态证据”“已通过运行时证据”“未验证”，后续阶段只能依赖前两类证据。

### 0B：legacy 数据不变量和归属风险报告

**目标**

- 为 legacy 项目回填建立可重复的只读基线。
- 找出 owner 表中的 NULL、孤儿引用、跨资源 mismatch、共享渠道、重复 slug、无文章人工工单和 URL import 重复提交风险。
- 同时检查 PostgreSQL 生产结构合同与 SQLite 测试结构合同的差异。

**边界**

- 有安全只读数据库连接时执行只读 SQL/查询；没有连接时只完成 schema/source 静态盘点，并把数据结果标记为 `UNVERIFIED`。
- 不修复数据、不创建 legacy 项目、不执行回填、不添加约束、不删除重复记录。
- 报告不得包含客户正文、密钥、完整 URL 中的敏感参数或个人信息；只保留计数、主键摘要和风险分类。

**最小验证**

- 产出带代码版本、数据库结构版本和查询时间的 invariant report。
- 每个异常都有：表/关系、检测规则、数量、样例 ID（必要时脱敏）、影响阶段和后续处理 owner。
- “没有发现异常”和“无法验证”必须严格区分；任何未分类异常都阻止阶段 0 通过。

### 0C：渠道归属模型决策和阶段 0 闸门

**目标**

- 根据 0A/0B 的事实，在“项目独占渠道”和“平台渠道 + 项目成员关系”之间作出明确选择。
- 规定 legacy 共享渠道的承载方式、密钥 scope、任务绑定规则、迁移处理和后续删除边界。

**边界**

- 只形成决策记录，不修改 `distribution_channels`、`task_distribution_channels` 或密钥存储。
- 如果现有事实不足以做选择，只输出待决问题和所需证据；不能把单值 `client_project_id` 直接写进后续迁移计划。
- 该决策只处理内部 GEOFlow 归属，不引入客户登录、客户 token、客户上传或外部资料接收层。

**最小验证**

- 形成一条不可歧义的 ADR/决策记录：选定模型、适用范围、legacy 例外、迁移前置条件和否决条件。
- 0C 通过条件是：0A 已确认目标版本、0B 没有未分类归属风险、渠道模型已冻结。

## 3. 交付物

阶段 0 完成时只允许产生以下交付物：

1. 版本与能力清单；
2. legacy invariant report；
3. 渠道归属模型决策记录；
4. 未验证项、阻塞项和阶段 1 输入清单；
5. 本阶段执行命令、读取范围和证据位置记录。

不得产生迁移文件、数据库写入、客户/项目记录、发布批次、外部渠道写操作或资料导入结果。

## 4. 阶段 0 完成/阻塞规则

### 允许进入阶段 1

- 目标代码版本已锁定；
- PostgreSQL/SQLite 结构合同的差异已记录；
- legacy owner、孤儿、NULL、跨项目候选 mismatch 和渠道共享关系均有结果或明确的 `UNVERIFIED` owner；
- 没有未分类的数据归属风险；
- 渠道独占或共享 membership 模型已作出明确决策。

### 必须停留在阶段 0

- 代码版本、部署分支或数据库结构无法确认；
- 发现数据风险但没有分类或处理 owner；
- 需要数据库只读访问而当前没有安全凭据；
- 渠道共享关系无法判断；
- 任何人要求通过静态扫描宣称迁移、回填或运行时测试已经成功。

## 5. Sol / 中等推理强度下的执行时间估计

这里的“时间”指本助手持续执行工具调用、阅读证据、整理报告和验证结果所需的有效时间，不是人员排期，也不包含等待用户决定、等待数据库凭据或等待外部系统响应。

| 工作包 | 具备只读数据库访问和可用发现命令 | 当前工作区的保守估计 |
| --- | --- | --- |
| 0A | 约 20–40 分钟 | 约 30–60 分钟；当前 PHP CLI 不可用，且未发现 GEOFlow discovery 脚本，需要增加静态替代盘点 |
| 0B | 约 45–90 分钟 | 约 60–120 分钟；没有数据库连接时只能完成 schema/source 风险报告，不能完成数据计数闭环 |
| 0C | 约 15–30 分钟 | 约 20–40 分钟；如果需要用户确认渠道模型，等待确认的时间另计 |
| 阶段 0 汇总 | 约 1.5–3 小时有效执行时间 | 约 2–4 小时有效执行时间；若缺少只读数据库访问，阶段 0 只能标记为“静态预检完成、运行时数据预检阻塞” |

Sol、推理强度中不会改变必须执行的检查项，也不能把不可用的运行时证据推断为已通过。当前最现实的结果是：先完成 0A 和 0B 的静态部分，确认是否能获得只读数据库证据，再完成 0C；阶段 0 是否“通过”取决于证据是否齐全，不取决于模型运行了多久。

## 6. 执行顺序

1. 先读取并记录工作区状态和依赖能力；
2. 执行 0A，形成版本/能力清单；
3. 执行 0B，优先使用只读数据库查询，缺失时明确列出 `UNVERIFIED`；
4. 根据 0A/0B 形成 0C 决策草案；
5. 汇总阶段 0 通过条件和阻塞项；
6. 阶段 0 通过前不修改阶段 1 的迁移、模型、权限或业务代码。
